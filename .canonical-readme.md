# triton-kernels

[![License: AGPL-3.0-or-later](https://img.shields.io/badge/License-AGPL--3.0--or--later-blue.svg)](LICENSE)

Three Triton kernels with end-to-end benchmark + correctness harnesses
against PyTorch references. Both fp32 and fp16 implementations
targeting Turing (GTX 1650, compute capability 7.5). Each kernel ships
its own correctness check, benchmark sweep, and JSON results.

> v0.1.0 was fp32-only. v0.2.0 adds fp16 variants (`01b`, `02b`, `03b`)
> alongside the originals. The fp16 flash-attention kernel routes
> through Turing's fp16 tensor-core MMA (m16n8k16) via `tl.dot` with
> an fp32 accumulator; this is what closes the gap to torch's
> `scaled_dot_product_attention` reference on Turing.

## What's in v0.2.0

### fp32 (v0.1.0, unchanged)

| Kernel | Status | Best speedup vs torch | Bandwidth saturated |
|---|---|---|---|
| `01_fused_softmax.py` | row-wise, numerically stable | **1.85×** at cols=16384 | ~96 GB/s |
| `02_fused_rmsnorm.py` | learnable scale, single-pass | **3.5×** at cols ≥ 512 | ~96 GB/s |
| `03_flash_attention.py` | FA-v2 forward, causal | **0.5–0.9×** (cuBLAS wins fp32 on Turing) | — |

### fp16 (new in v0.2.0)

| Kernel | Best speedup vs torch fp16 | Speedup vs fp32 Triton (this repo) |
|---|---|---|
| `01b_fused_softmax_fp16.py` | **2.88×** at cols=2048 (1.00× at cols ≥ 8192) | **~2×** wall-clock at every cols (fp16 halves bytes moved) |
| `02b_fused_rmsnorm_fp16.py` | **4.20×** at cols=1024 | **~2×** wall-clock at every cols |
| `03b_flash_attention_fp16.py` | **1.05–1.29×** for M ∈ {256, 512, 1024, 2048}; **0.47×** at M=128 | **2.4×–4.7×** at M ∈ {128…2048} |

All six kernels pass correctness checks:

- Softmax fp32 vs `torch.softmax` (fp32): `max_abs_err ≤ 1.12e-08`
- Softmax fp16 vs `torch.softmax` (fp16): `max_abs_err ≤ 7.63e-06` (atol=1e-2)
- RMSNorm fp32 vs `torch.nn.functional.rms_norm` (fp32): `max_abs_err ≤ 1.91e-06`
- RMSNorm fp16 vs `torch.nn.functional.rms_norm` (fp16): `max_abs_err ≤ 7.81e-03` (atol=1e-2)
- Flash-Attention fp32 vs `softmax(QK^T*scale)@V` (fp32): `max_abs_err ≤ 3.35e-08`
- Flash-Attention fp16 vs `torch.nn.functional.scaled_dot_product_attention` (fp16): `max_abs_err ≤ 3.05e-05` (atol=1e-2)

## Honest reading of the fp16 numbers

The **fp16 softmax** wins at the column sizes where torch's fp16
softmax happens to be inefficient (cols=2048: 2.88×) and matches at
cols ≥ 8192 where torch is also bandwidth-saturating. Bandwidth
saturates at the same ~96 GB/s as fp32 — the kernel was already
memory-bound at fp32, so the fp16 win comes from *halving the bytes
moved*, not from any tensor-core path (softmax has no matmul).

The **fp16 RMSNorm** holds its consistent 3.5–4.2× speedup vs the
torch two-pass reference at fp16 too, and roughly doubles in
wall-clock vs the fp32 Triton kernel because of halved HBM traffic.
Same ~96 GB/s saturation.

The **fp16 flash-attention** is the load-bearing v0.2.0 result.
Switching `tl.dot` to fp16 inputs with `out_dtype=tl.float32` routes
the two matmul steps (Q@K^T and P@V) through Turing's m16n8k16 fp16
mma instructions, the same tensor-core path torch's reference uses.
The numbers:

- **vs fp32 Triton (this repo, same algorithm):** 1.07× at M=128,
  rising to **4.66×** at M=2048. This is the "closes the gap"
  result the v0.1 README pre-registered.
- **vs torch fp16 reference (`scaled_dot_product_attention`):**
  - M=128: 0.47× — torch dispatches an efficient short-sequence
    path at small M; we lose.
  - M=256: 1.29×
  - M=512: 1.23×
  - M=1024: 1.10×
  - M=2048: 1.05×

At M ≥ 256 the Triton fp16 forward edges out torch's SDPA fp16
reference by 5–29%. The result is modest because torch's reference is
itself a tuned tensor-core path on Turing, but the v0.1 non-victory
("Triton SIMT fp32 loses 2–3× to cuBLAS-TF32") is resolved by moving
both implementations to the same precision class. The 0.47× at
M=128 is documented honestly: torch wins the small-sequence regime.

### A Turing-specific surprise worth naming

The original launch configuration (`BLOCK_M=BLOCK_N=64`, `num_warps=4`)
inherited from the fp32 kernel was **catastrophic** for the fp16 path:
~6× slower than the tuned launch parameters at M=512. An offline sweep
showed that `BLOCK_M=BLOCK_N=32`, `num_warps=4`, `num_stages=2` is the
robust pick across M=128…2048 for fp16 on this GPU. The fp16
tensor-core mma instruction has different register-pressure and
occupancy characteristics from the fp32 SIMT FMA path; tile sizing
does not transfer across precisions. This is what real `@triton.autotune`
is for, deferred to v0.3.

## What is *not* in v0.2.0

- **bf16.** Turing's tensor cores do not implement bf16 mma — that
  instruction was added with Ampere. Adding `tl.dot` on bf16 inputs
  on this GPU would silently fall back to a non-tensor-core path; not
  worth the surface-area increase here. bf16 is a v0.3 item on Ampere
  or newer hardware.
- **fp8.** Hopper-only (E4M3 / E5M2 mma); not on Turing.
- **TF32-explicit hints.** `torch.backends.cuda.matmul.allow_tf32`
  policy is whatever the venv default sets. The v0.1 plan to ship
  TF32-on / TF32-off reference columns is deferred to v0.3 — the
  fp16 result above already addresses the v0.1 "cuBLAS uses TF32"
  observation by moving both implementations to fp16.
- **`@triton.autotune`** over a `BLOCK_M / BLOCK_N / num_warps /
  num_stages` grid. The v0.2 fp16 flash-attention launch config is a
  hard-coded pick from an offline sweep on this GPU; that pick won't
  transfer to other hardware. Autotune is a v0.3 item.
- **Flash-attention backward.** Forward only. Backward needs the
  saved log-sum-exp + dO statistics; that's a separate kernel of
  similar size.
- **Fused-RMSNorm-Linear.** Single-kernel norm+gemm. Still deferred
  to v0.3 — Turing's 64 KB SMEM per SM constrains tile sizing tightly
  and deserves its own artifact.
- **ROCm / AMD path.** NVIDIA Turing only for this artifact.

## Build / run

Requires the Triton+PyTorch venv (needs `LD_LIBRARY_PATH=/usr/lib`
for `libz.so.1` on this Arch+nix setup):

```sh
# fp32 kernels (v0.1.0)
triton-python kernels/01_fused_softmax.py
triton-python kernels/02_fused_rmsnorm.py
triton-python kernels/03_flash_attention.py

# fp16 variants (v0.2.0)
triton-python kernels/01b_fused_softmax_fp16.py
triton-python kernels/02b_fused_rmsnorm_fp16.py
triton-python kernels/03b_flash_attention_fp16.py

# Save benchmark JSON
triton-python kernels/01b_fused_softmax_fp16.py --bench --out bench/01b_fused_softmax_fp16.json
triton-python kernels/02b_fused_rmsnorm_fp16.py --bench --out bench/02b_fused_rmsnorm_fp16.json
triton-python kernels/03b_flash_attention_fp16.py --bench --out bench/03b_flash_attention_fp16.json
```

`triton-python` is a thin shell wrapper at `~/.local/bin/triton-python`
that sets `LD_LIBRARY_PATH=/usr/lib`; substitute `python` if your env
doesn't need that.

## Reproducibility

- Hardware: NVIDIA GeForce GTX 1650 with Max-Q Design (Turing,
  compute capability 7.5, 3.9 GB device memory).
- Software: Triton 3.7.0, PyTorch 2.5.1+cu121, CUDA 13.2, Arch Linux
  kernel 7.0.3.
- Bench shapes seeded with `torch.manual_seed(0)`. fp32 reductions are
  bit-deterministic; fp16 reductions have visible round-off vs the
  torch reference, captured by the `atol=1e-2, rtol=1e-2` correctness
  tolerance and reported `max_abs_err` per case.
- Timings are wall-clock over 100 (softmax/rmsnorm) or 50/20
  (flash-attention) iterations after 3 warm-up iterations, with
  `torch.cuda.synchronize()` between runs. All JSON in `bench/`.

## Evidence vocabulary

- `compiled` — yes, Triton 3.7.0 / PyTorch 2.5.1+cu121.
- `unit-tested` — correctness checks per kernel pass at the
  tolerances quoted above (fp32: atol=1e-5 / atol=1e-4 / atol=1e-3;
  fp16: atol=1e-2 across all three).
- `benchmarked` — wall-clock timings with warmup + sync, JSON in
  `bench/`.
- `hardware-verified` — measured on GTX 1650 Max-Q (Turing, cc 7.5).

Words *not* used: "production", "verified" (without tolerance +
reference), "fast" (without a specific reference + shape), "optimized."

## What this work is for

This repo is the kernel-stack-fluency artifact in a research agenda
focused on agentic-safety substrate work. ML systems / kernels is the
cross-domain competence layer — knowing the GPU stack well enough to
debug an attention-path bottleneck in a frontier-model deployment,
rather than to compete with the cuBLAS / cutlass / FlashAttention
teams who own that surface.

The discipline above (pre-registered shape sweep, correctness checks
before performance numbers, honest non-claims where the kernel loses
to the reference) is the same discipline that runs through the rest
of the `github.com/SMC17` fleet.
