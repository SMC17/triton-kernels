# triton-kernels

[![License: AGPL-3.0-or-later](https://img.shields.io/badge/License-AGPL--3.0--or--later-blue.svg)](LICENSE)

Triton kernels with end-to-end benchmark + correctness harnesses
against PyTorch references. Both fp32 and fp16 forward implementations
plus an fp32 backward for flash-attention; all targeting Turing
(GTX 1650, compute capability 7.5). Each kernel ships its own
correctness check, benchmark sweep, and JSON results.

> v0.1.0 was fp32-only. v0.2.0 added fp16 variants (`01b`, `02b`,
> `03b`) alongside the originals. v0.3.0 wraps all six kernels in
> `@triton.autotune` over a (num_warps, num_stages) grid for the
> reduction kernels and a (BLOCK_M, BLOCK_N, num_warps, num_stages)
> grid for flash-attention — closing v0.2.0's documented finding
> that tile-size choices do not transfer across precisions. v0.4.0
> adds the flash-attention v2 BACKWARD pass (fp32, causal optional)
> following Dao 2023, with an optional `save_lse` flag on both
> forward kernels.

## What's in v0.4.0

Flash-attention v2 BACKWARD pass (fp32, causal optional). Algorithmic
completeness: the v0.3 forward saves no statistics; v0.4 saves the
per-row log-sum-exp on demand and uses it to recompute the softmax
inside the backward kernels stably, without materializing the
N×M attention matrix at any point.

### Backward correctness vs PyTorch autograd

Reference: `softmax(Q @ K^T * scale + causal_mask) @ V` with
`.backward(dO=ones_like)`. Tolerance `atol=1e-3, rtol=1e-3`.

| Case (B, H, M, D, causal) | dQ max err | dK max err | dV max err |
|---|---|---|---|
| (1, 1, 64, 64, False)  | 2.10e-09 | 3.26e-09 | 2.38e-07 |
| (1, 1, 64, 64, True)   | 2.79e-09 | 5.59e-09 | 9.54e-07 |
| (1, 4, 128, 32, True)  | 6.54e-09 | 1.49e-08 | 7.15e-07 |
| (1, 4, 256, 64, True)  | 6.62e-09 | 2.98e-08 | 9.54e-07 |
| (2, 4, 256, 64, True)  | 8.09e-09 | 2.05e-08 | 9.54e-07 |
| (1, 8, 512, 64, True)  | 5.59e-09 | 2.42e-08 | 1.91e-06 |
| (1, 4, 1024, 64, True) | 6.50e-09 | 4.10e-08 | 1.43e-06 |

All 7 cases pass. Largest observed error is `1.91e-06` (dV at
M=512 causal) — three orders of magnitude below the tolerance.

### Backward perf vs torch autograd

The Triton backward at M ≤ 512 is faster than torch's full
forward+backward pipeline; at M ≥ 1024 it loses.

| M | triton bwd (us) | torch fwd+bwd (us) | triton bwd TFLOPS | ratio (torch fwd+bwd ÷ triton bwd) |
|---|---|---|---|---|
| 128 | 446.70 | 734.15 | 0.094 | 1.64× |
| 256 | 768.13 | 1103.76 | 0.218 | 1.44× |
| 512 | 2137.44 | 2925.12 | 0.314 | 1.37× |
| 1024 | 6730.26 | 4752.52 | 0.399 | 0.71× |
| 2048 | 26153.21 | 18517.79 | 0.411 | 0.71× |

**Honest non-claim:** this is NOT an apples-to-apples comparison.
Torch's autograd path does not expose a backward-only entry point
that takes a precomputed forward output + dO, so the torch column
times the full forward+backward through `.backward()`. The Triton
column is the backward-only call. Because the torch column includes
the forward, the true backward-vs-backward gap at large M is
*larger* than what this table shows — at M ≥ 1024 the Triton fp32
backward loses to torch's tuned tensor-core autograd. Closing that
gap is what an fp16 backward (v0.4.1) would address by routing the
five matmul steps (Q@K^T, dO@V^T, P^T@dO, dS^T@Q, dS@K) through the
same Turing m16n8k16 tensor cores that the v0.3 fp16 forward uses.

### Forward changes for the backward consumer

Both `03_flash_attention.py` (fp32) and `03b_flash_attention_fp16.py`
(fp16) gain an optional `save_lse: bool` kwarg. When `True`, the
kernel writes `L_i = m_i + log(l_i)` (fp32, shape `[B, H, M]`) to
an output buffer alongside `O`. Default is `False` for back-compat;
the existing v0.3.0 correctness cases pass unchanged with the new
optional output. The fp32 module also exports a convenience wrapper
`triton_flash_attn_with_lse(...)` that always saves LSE.

The fp16 forward gains the `save_lse` path even though the v0.4
backward is fp32-only — keeps the forward contract consistent and
puts the LSE buffer in place for the v0.4.1 fp16 backward.

### Backward kernel structure (Dao 2023 Section 3)

Three-kernel structure:

1. **Preprocess** — `D_i = sum(dO_i * O_i, axis=-1)` (fp32 [B, H, M]).
   Bandwidth-bound, fixed `BLOCK_M=64`, no autotune.
2. **dK / dV** — outer loop over K/V blocks along N, inner over Q
   blocks along M. Accumulates `dK_j, dV_j` in registers; writes
   once at end. Causal-aware: skips Q blocks below the K block
   when `IS_CAUSAL=True`.
3. **dQ** — outer loop over Q blocks along M, inner over K/V
   blocks along N. Mirror image of the forward iteration pattern.

Per Dao 2023, no kernel materializes the N×M attention matrix.
P_ij is recomputed inside the inner loop from Q, K and the saved
per-row LSE.

Both backward kernels wrapped in `@triton.autotune` keyed on
`(M, N, D_HEAD)` over `BLOCK_M ∈ {32, 64} × BLOCK_N ∈ {32, 64} ×
num_warps ∈ {4, 8}` at `num_stages=2`. The backward holds more live
tiles than the forward — Q, K, V, dO at minimum, plus running
dK/dV/dQ accumulators — so the SMEM estimator uses a 4× multiplier
(vs the forward's 2×); 4 configs survive the budget filter.

## What's in v0.3.0

All six kernels now select their launch configuration with
`@triton.autotune`. The autotuner keys on `n_cols` for softmax /
RMSNorm and on `(M, N, D_HEAD)` for flash-attention; the first
invocation at a new key benchmarks every config in the grid and
caches the winner.

### Headline result: flash-attention fp32

The v0.1 / v0.2 fp32 flash-attention used a hand-picked
`BLOCK_M=BLOCK_N=64, num_warps=4, num_stages=2` config and lost to
torch's `scaled_dot_product_attention` reference at every measured
shape (speedup 0.45–0.91×). Autotuning over a 36-config grid
(27 live after Turing 64 KB SMEM pruning) **inverts that result**:

| M | v0.2 us | v0.3 us | v0.2 vs ref | v0.3 vs ref | autotune pick |
|---|---|---|---|---|---|
| 128 | 241.96 | 137.58 | 1.10× | **1.55×** | BLOCK 64×64, nw=8, ns=2 |
| 256 | 754.74 | 154.55 | 0.47× | **1.91×** | BLOCK 16×32, nw=2, ns=3 |
| 512 | 2474.66 | 515.21 | 0.45× | **2.21×** | BLOCK 32×32, nw=2, ns=2 |
| 1024 | 8205.14 | 1891.34 | 0.54× | **2.41×** | BLOCK 64×64, nw=8, ns=2 |
| 2048 | 32146.83 | 7304.04 | 0.58× | **2.63×** | BLOCK 64×64, nw=8, ns=2 |

The v0.1 / v0.2 fp32 numbers were taken with a measured-good config
for fp32 small-tile arithmetic that happened to be wrong for the
SIMT-on-Turing path; autotuning finds that `num_warps=8` at
BLOCK_M=BLOCK_N=64 is the actual best for M ≥ 1024, and a smaller
BLOCK_M=16 at M=256 lets the kernel issue more programs in parallel.
The 2.6× headline at M=2048 is the autotune-vs-hand-tuned delta.

### Flash-attention fp16

| M | v0.2 us | v0.3 us | v0.2 vs torch | v0.3 vs torch | autotune pick |
|---|---|---|---|---|---|
| 128 | 225.42 | 99.74 | 0.47× | **1.02×** | BLOCK 32×32, nw=4, ns=2 |
| 256 | 309.44 | 161.30 | 1.29× | **1.34×** | BLOCK 16×32, nw=2, ns=3 |
| 512 | 893.51 | 522.52 | 1.23× | **1.22×** | BLOCK 32×32, nw=4, ns=3 |
| 1024 | 1854.35 | 1897.88 | 1.10× | **1.08×** | BLOCK 32×32, nw=4, ns=3 |
| 2048 | 6904.24 | 7212.97 | 1.05× | **1.02×** | BLOCK 32×32, nw=4, ns=3 |

The M=128 loss in v0.2.0 (0.47× vs torch's small-sequence SDPA path)
is **closed** by autotuning — we now match torch at M=128 instead of
losing 2.1×. At M ≥ 256 the v0.2.0 hand-tuned `(32, 32, 4, 2)` was
already near-optimal; autotune confirms it for M=128 and finds a
slightly different pick (`(16, 32, 2, 3)`) at M=256 worth ~5%, and
`num_stages=3` (instead of 2) at M=512+ worth ~5% as well. Above
M ≥ 1024 the delta is in the noise.

### Softmax / RMSNorm (fp32 and fp16)

These kernels were already bandwidth-saturated at v0.2.0 (~96 GB/s
of the GTX 1650's ~128 GB/s theoretical). Autotune over
(num_warps × num_stages) keeps them at that saturation point and
matches v0.2.0 speedups to within ±5% across all column sizes ≥ 512.
At cols ≤ 256 (the launch-overhead-bound regime), the autotuner's
choice for the softmax kernels lands on `num_warps=2, num_stages=4`
where v0.2.0's heuristic picked `num_warps=4, num_stages=2`; the
resulting timings are within measurement noise (sub-200us kernels on
a consumer Turing GPU vary ±20% per run with clock-state jitter).

Honest read: softmax and RMSNorm did not benefit from autotuning on
this GPU. They were already at the right config for their
bandwidth-bound regime. The v0.3.0 win is the flash-attention fp32
inversion above; the fp16 win at M=128 is the secondary headline.

## Cumulative correctness (unchanged from v0.2.0)

- Softmax fp32 vs `torch.softmax` (fp32): `max_abs_err ≤ 1.12e-08`
- Softmax fp16 vs `torch.softmax` (fp16): `max_abs_err ≤ 7.63e-06` (atol=1e-2)
- RMSNorm fp32 vs `torch.nn.functional.rms_norm` (fp32): `max_abs_err ≤ 1.91e-06`
- RMSNorm fp16 vs `torch.nn.functional.rms_norm` (fp16): `max_abs_err ≤ 7.81e-03` (atol=1e-2)
- Flash-Attention fp32 vs `softmax(QK^T*scale)@V` (fp32): `max_abs_err ≤ 3.17e-08`
- Flash-Attention fp16 vs `torch.nn.functional.scaled_dot_product_attention` (fp16): `max_abs_err ≤ 3.05e-05` (atol=1e-2)

## Config-space pruning

The flash-attention autotune grid is `BLOCK_M ∈ {16, 32, 64} ×
BLOCK_N ∈ {32, 64} × num_warps ∈ {2, 4, 8} × num_stages ∈ {2, 3}`
(36 configs). Configs whose double-buffered K+V SMEM footprint
exceeds Turing's 64 KB/SM budget are filtered out at autotune
construction time:

- fp32: 9 configs pruned by SMEM (27 alive). The largest pruned
  config is `BLOCK_N=64, num_stages=3` (98 KB).
- fp16: 0 configs pruned (36 alive). fp16 halves the SMEM cost so
  every config in the grid fits.

The grid is intentionally narrower than the task-spec maximum of 81.
Each new (M, N, D_HEAD) key triggers a full sweep on first
invocation; with the wider grid the sweep ran for hours on a single
GTX 1650. The narrower grid covers the interesting region and still
finds the v0.2 hand-tuned `(32, 32, 4, 2)` pick for M=128 fp16
(reproducing v0.2's offline-sweep result automatically).

If a future winner lands on the {32, 64} BLOCK_N edge or the {2, 3}
num_stages edge, the boundary should be widened.

## Honest reading of the fp16 numbers (unchanged from v0.2.0)

The **fp16 softmax** wins at the column sizes where torch's fp16
softmax happens to be inefficient (cols=2048: ~1.6× autotuned) and
matches at cols ≥ 8192 where torch is also bandwidth-saturating.
Bandwidth saturates at ~96 GB/s on this GPU — the kernel was already
memory-bound at fp32, so the fp16 win comes from *halving the bytes
moved*, not from any tensor-core path (softmax has no matmul).

The **fp16 RMSNorm** holds its consistent 3.5–3.7× speedup vs the
torch two-pass reference at fp16 too, and roughly doubles in
wall-clock vs the fp32 Triton kernel because of halved HBM traffic.

The **fp16 flash-attention** is still the load-bearing precision
result. Switching `tl.dot` to fp16 inputs with `out_dtype=tl.float32`
routes the two matmul steps (Q@K^T and P@V) through Turing's
m16n8k16 fp16 mma instructions, the same tensor-core path torch's
reference uses. Autotune confirms the v0.2 finding that
BLOCK_M=BLOCK_N=32 is the right pick across M ≥ 128 fp16, and
upgrades `num_stages` from 2 → 3 at M ≥ 512.

### A Turing-specific surprise worth naming (preserved from v0.2.0)

The original v0.1 / v0.2 fp32 flash-attention configuration
(`BLOCK_M=BLOCK_N=64`, `num_warps=4`) was *catastrophic* for the
fp16 path: ~6× slower than the tuned parameters at M=512. An
offline sweep in v0.2 showed that `BLOCK_M=BLOCK_N=32, num_warps=4,
num_stages=2` is the robust pick across M=128…2048 for fp16 on this
GPU. v0.3 confirms this automatically: the autotuner reaches the
same `(32, 32, 4, 2)` config at M=128 and stays close (`num_stages=3`
above M=512) for the rest of the sweep. The fp16 tensor-core mma
instruction has different register-pressure and occupancy
characteristics from the fp32 SIMT FMA path; tile sizing does not
transfer across precisions, and v0.3 is what makes that
transfer-failure recoverable per shape rather than a manual offline
sweep per release.

## What is *not* in v0.4.0

- **fp16 backward** (→ v0.4.1). The recomputation of P inside the
  backward has tighter numerical-stability constraints than the
  forward; a small fp16 error in S_ij propagates through `exp` into
  P, through `P^T @ dO` into dV, and the cumulative error can blow
  past the fp16 forward's `atol=1e-2` tolerance. The fp16 forward
  already saves LSE (fp32) per the v0.4.0 forward modification, so
  the consumer is in place; only the backward kernel itself is
  pending.
- **Variable-length sequences / arbitrary attention masks** (→ v0.5).
  Strict causal is supported. Non-causal masks would need a per-row
  mask infrastructure that doesn't transfer from the forward's
  `n_offs < N` pattern.
- **Dropout in forward and backward** (→ v0.5+). Standard FA-2
  supports dropout with a shared RNG state across the two passes;
  v0.4 ships without to keep the diff focused.
- **Triton-side gradient checkpointing.** The backward recomputes
  the attention scores and softmax from Q, K, V and the saved LSE,
  but does not implement a separate activation-save tier.
- **bf16.** Turing's tensor cores do not implement bf16 mma — that
  instruction was added with Ampere. Not on this GPU.
- **fp8.** Hopper-only (E4M3 / E5M2 mma); not on Turing.
- **TF32-explicit hints.** `torch.backends.cuda.matmul.allow_tf32`
  policy is whatever the venv default sets. The v0.2 fp16 result
  already addresses the v0.1 "cuBLAS uses TF32" observation by
  moving both implementations to fp16.
- **Fused-RMSNorm-Linear.** Single-kernel norm+gemm. Turing's
  64 KB SMEM per SM constrains tile sizing tightly and deserves its
  own artifact.
- **ROCm / AMD path.** NVIDIA Turing only.
- **Persistent per-disk autotune cache across processes.** Triton
  caches the winning config in memory per Python process; first
  invocation at a new key on a fresh process still triggers the
  sweep. `triton.runtime.autotuner.Autotuner` exposes a disk cache
  hook (`save_path` / `restore_value`) that a future revision could
  wire up.

## Build / run

Requires the Triton+PyTorch venv (needs `LD_LIBRARY_PATH=/usr/lib`
for `libz.so.1` on this Arch+nix setup):

```sh
# Correctness + benchmark (all kernels)
triton-python kernels/01_fused_softmax.py
triton-python kernels/01b_fused_softmax_fp16.py
triton-python kernels/02_fused_rmsnorm.py
triton-python kernels/02b_fused_rmsnorm_fp16.py
triton-python kernels/03_flash_attention.py
triton-python kernels/03b_flash_attention_fp16.py
triton-python kernels/04_flash_attention_backward.py

# Save benchmark JSON (with autotune winning configs annotated)
triton-python kernels/01_fused_softmax.py        --bench --out bench/01_fused_softmax_autotuned.json
triton-python kernels/01b_fused_softmax_fp16.py  --bench --out bench/01b_fused_softmax_fp16_autotuned.json
triton-python kernels/02_fused_rmsnorm.py        --bench --out bench/02_fused_rmsnorm_autotuned.json
triton-python kernels/02b_fused_rmsnorm_fp16.py  --bench --out bench/02b_fused_rmsnorm_fp16_autotuned.json
triton-python kernels/03_flash_attention.py      --bench --out bench/03_flash_attention_autotuned.json
triton-python kernels/03b_flash_attention_fp16.py --bench --out bench/03b_flash_attention_fp16_autotuned.json
triton-python kernels/04_flash_attention_backward.py --bench --out bench/04_flash_attention_backward.json
```

First-invocation cost: with autotune, the first launch at a new key
runs all configs and benchmarks them. Each kernel's bench script
warms up before timing, so the timing loop sees the cached winner;
the autotune sweep itself runs during the warmup phase. The
flash-attention benchmark over five shapes (M = 128…2048) takes
~90s wall-clock on the GTX 1650; softmax and RMSNorm sweeps run in
under 30s.

`triton-python` is a thin shell wrapper at `~/.local/bin/triton-python`
that sets `LD_LIBRARY_PATH=/usr/lib`; substitute `python` if your env
doesn't need that.

## Reproducibility

- Hardware: NVIDIA GeForce GTX 1650 with Max-Q Design (Turing,
  compute capability 7.5, 3.9 GB device memory).
- Software: Triton 3.7.0, PyTorch 2.5.1+cu121, CUDA 13.2, Arch Linux
  kernel 7.0.3.
- Bench shapes seeded with `torch.manual_seed(0)`. fp32 reductions are
  bit-deterministic; fp16 reductions have visible round-off vs the
  torch reference, captured by the `atol=1e-2, rtol=1e-2` correctness
  tolerance and reported `max_abs_err` per case.
- Timings are wall-clock over 100 (softmax/rmsnorm) or 50/20
  (flash-attention) iterations after 3 warm-up iterations, with
  `torch.cuda.synchronize()` between runs. Autotune cache is
  populated during warm-up, so timing iterations see the cached
  winning config. All JSON in `bench/`, with the v0.3 files
  suffixed `_autotuned.json`.
- Sub-200us kernels on this GTX 1650 vary ±20% per run with
  power/clock-state jitter; comparisons in that regime should be
  treated as within-noise unless the delta exceeds 2×.

## What this work is for

This repo is the kernel-stack-fluency artifact in a research agenda
focused on agentic-safety substrate work. ML systems / kernels is the
cross-domain competence layer — knowing the GPU stack well enough to
debug an attention-path bottleneck in a frontier-model deployment,
rather than to compete with the cuBLAS / cutlass / FlashAttention
teams who own that surface.

The discipline above (pre-registered shape sweep, correctness checks
before performance numbers, honest non-claims where the kernel does
not improve on the reference) is the same discipline that runs
through the rest of the `github.com/SMC17` fleet.
